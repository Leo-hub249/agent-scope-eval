**Proposed fix (for scheduling)**

1. **Immediate, low risk:** recreate the index. Run it as the table owner or admin, outside a transaction, so it does not lock writes:
   `CREATE INDEX CONCURRENTLY shipment_events_order_id_idx ON shipment_events (order_id, at DESC);`
   Including `at DESC` lets the latest-event lookup read a single index entry. I have not run this, so the expected speed-up is based on the plan above and is not measured.
2. **Code follow-up:** replace the per-order loop with one query that fetches each order's latest event, for example a `LATERAL` join or `DISTINCT ON (order_id)`. That removes the N+1 pattern and makes the endpoint's cost independent of order count.
3. **Consider:** an index on `orders (customer_id)`. It is also missing and the orders query currently does a sequential scan. It is small today (6,000 rows), but it will matter as the table grows.
