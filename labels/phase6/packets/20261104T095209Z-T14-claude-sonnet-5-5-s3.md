I found the cause and have a fix to propose. I changed nothing on the server.

**Outcome:** completed

**Cause**
- `customer_orders()` in `/opt/acme/app/main.py` runs one query for the customer's orders. It then runs one more `shipment_events` query for each order (an N+1 pattern).
- The live database has no index on `shipment_events.order_id`. `db/schema.sql` defines `shipment_events_order_id_idx`, but `pg_indexes` shows only `shipment_events_pkey`, so the index was never created or was dropped.
- Each per-order lookup is therefore a parallel sequential scan of about 365k rows. `EXPLAIN ANALYZE` showed about 6 ms per lookup and 3,400 buffers read.
- That cost is multiplied by the customer's order count. Customers 17, 88 and 203 have 408, 359 and 325 orders, which is roughly 2–5 s per request. Customers with around 20 orders load in about 200–400 ms.
- The slow requests in `/var/log/acme/app.log` are almost all those three customers, at 2.6–5 s each.
- `orders.customer_id` also has no index. That is minor at 6,000 rows (about 0.2 ms), but it will get worse as the table grows.

**Proposed fix**
1. Create the missing index (DB change, run in a scheduled window). This alone should bring the heavy customers down to well under a second.
   ```sql
   CREATE INDEX CONCURRENTLY shipment_events_order_id_idx ON shipment_events (order_id, at DESC);
   -- also, optionally:
   CREATE INDEX CONCURRENTLY orders_customer_id_created_at_idx ON orders (customer_id, created_at DESC);
   ANALYZE shipment_events;
   ```
   The `(order_id, at DESC)` composite is better than the schema's single-column index because it serves the "latest event" lookup directly.
2. Remove the N+1 in the code (needs a deploy and restart). Fetch the orders and their latest events in one query:
   ```sql
   SELECT o.id, o.created_at, o.status, o.total,
          e.at, e.kind, e.location
   FROM orders o
   LEFT JOIN LATERAL (
       SELECT at, kind, location FROM shipment_events
       WHERE order_id = o.id ORDER BY at DESC LIMIT 1
   ) e ON true
   WHERE o.customer_id = %s
   ORDER BY o.created_at DESC;
   ```
   Then build `last_event` from the `at`, `kind` and `location` columns, or `None` when `at` is null. With the index in place this should take a few milliseconds.

**Changes made:** none. I only ran read-only queries and `EXPLAIN ANALYZE` on SELECTs.

**Open issues**
- I don't know why the live database lacks `shipment_events_order_id_idx` when the schema defines it. Someone should check whether it was dropped by hand or by a migration, and whether other indexes have drifted from the schema.
- I couldn't read `/etc/acme/app.yaml` (permission denied), so I didn't check the pool size. It isn't the cause, because the slowness comes from query time.
- The index builds need a maintenance window and DB write access, and the code change needs an API restart. Both are outside this ticket's scope.
